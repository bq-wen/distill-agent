# 整体架构：一条运行时，两张子图

## 1. 一句话

**给一个原始资料目录，蒸馏流水线把它加工成可检索的知识库；在线分身（另一张图）只读检索这个知识库来回答问题。** 两张图共用同一个自研图运行时 WenGraph，用同一套治理框架管两种完全不同的风险场景。

## 2. 全景图

```
┌─────────────── 蒸馏链路（后台，SUPERVISED 模式） ───────────────┐
│ 原始资料目录(聊天/简历/README/Git历史)                           │
│    → SourceLoader(载入) → Cleaner(清洗) → Extractor(LLM提炼)     │
│    → Structurer(结构化) → AuditGate(人工审批闸门) → Indexer(写库) │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 审核通过的知识文档
                               ▼
                  ┌──────────────────────────┐
                  │ SQLite 知识库             │
                  │ · 语义向量(本地embedding) │
                  │ · FTS5 关键词索引         │
                  └────────────┬─────────────┘
                               │ 混合检索（只读）
┌─────────────── 展示链路（在线，UNATTENDED 模式） ───────────────┐
│ 访客提问 → LLMNode(ReAct) → AgentRouter → ToolGuard → ToolNode  │
│           → LLMNode(带检索结果) → 回答 + 引用                    │
│ persona 由 profile 文档动态生成                        │
└─────────────────────────────────────────────────────────────────┘
```

## 3. 关键设计决策（面试必答）

### 3.1 为什么自研图运行时，不用 LangChain？

- 面试回答要点：**可控性**。LangChain 的图是"组装出来的"，中间的安全决策（谁能调用工具、当前模式允不允许执行）是外挂的；WenGraph 把治理内建为图的一等公民（ToolGuard 节点、策略路由节点）。
- 代价是开发量和兼容性风险，所以本项目把 WenGraph 作为固定版本的 git submodule（`vendor/wengraph`），应用层只通过 `personal_agent/wengraph_runtime.py` 一个导入边界使用它。

### 3.2 为什么两条链路共用一个运行时？

- 因为治理模型是**同构的**：都是"节点发出工具请求 → 门卫检查 → 路由决策"。区别只在参数：
  - 展示链路：`UNATTENDED` + 只读工具（LOW risk）→ 全自动放行
  - 蒸馏链路：`SUPERVISED` + 写库工具（MEDIUM/HIGH risk）→ **自动暂停等人工审批**
- 于是"蒸馏结果必须人工审核"不是额外代码，而是治理框架免费给的。这是本项目的系统设计叙事核心。

### 3.3 为什么检索不用向量数据库？

- 单机演示场景：SQLite 一张表存向量 + FTS5 存关键词，零外部依赖，Docker 一键起。
- 面试回答：**根据容量选型**。几千条 chunk 的规模下，暴力余弦 + 阈值过滤毫秒级返回；引入 Milvus/pgvector 是当规模与并发上来后的迁移路径，不是演示期的默认解。

### 3.4 为什么是"202 + 轮询"而不是同步等待？

- LLM 生成耗时（秒级），同步请求会占满连接；返回 `202 Accepted` + `run_id`，前端轮询 `/api/runs/{id}`，把"提交"和"结果"解耦。
- 队列是进程内的有界 `asyncio.Queue` + 固定数量 worker：容量可控（队列满返回 429），代价是**只能单进程部署**（README 已写明横向扩展路径是 Redis/Celery 共享调度）。

## 4. 数据契约

四类核心数据结构，是"模板化"的骨架（展示链路的契约已实现，蒸馏链路契约随蒸馏任务落地）：

四类核心数据结构，是"模板化"的骨架：

| 契约 | 位置 | 作用 |
|---|---|---|
| `KnowledgeAtom` | 蒸馏中间产物 | 可溯源的知识原子（来源文件、类型、置信度） |
| `KnowledgeDocument` | 知识库文档 | front matter + Markdown，扩展 `public_questions`/`topics` |
| `ProfileDocument` | 身份文档 | 驱动 persona、名字、monogram、推荐问题 |
| `AuditArtifact` | 审批产物 | approved/rejected 列表，决定哪些原子进库 |

## 5. 技术栈速查

| 层 | 技术 | 用途 |
|---|---|---|
| 运行时 | WenGraph（自研） | 受控 ReAct 图 + 工具治理 |
| 后端 | Python 3.12 / FastAPI / Pydantic v2 | HTTP 传输边界、契约 |
| 并发 | asyncio + 有界 Queue + 固定 worker | 容量可控的异步执行 |
| 存储 | SQLite（WAL）+ 本地 embedding（bge-small-zh） | 知识索引 + FTS5 |
| 前端 | React 18 + TypeScript + Vite | 单页聊天界面 |
| 部署 | Docker + compose + Nginx（模板打包任务） | 单机上线 |

## 6. 面试开场白（30 秒版本）

> "我做的项目是一个通用数字分身模板：你把一个人的资料放进来，蒸馏流水线自动加工成知识库，线上就多了一个只读检索这些资料的 AI 分身。核心是一个自研的图运行时，同一套工具治理框架管两条链路——在线服务是无人值守的只读检索，后台蒸馏是带人工审批闸门的写库流程。"
